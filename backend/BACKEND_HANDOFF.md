# WindFlow AI: handoff для frontend и защиты

Актуально: 23 сентября 2026. Владелец этого файла — backend-агент.
Frontend-агент работает только в `frontend/**`, `README.md`, `docs/**`.
После разделения ролей backend-агент эти файлы не меняет, кроме прямых новых поручений пользователя.

**Новое поручение пользователя:** README объясняет продукт, технологии, установку, запуск и проверку решения для внешнего читателя. Не возвращать туда внутренние статусы «цель не достигнута», сообщения об окружении разработки, планы экспериментов и сценарий выступления. По этому поручению README приведён к указанному формату. Реальные метрики и технический протокол доступны по ссылкам; итоговые метрики интерфейс берёт из API.

**Обновление моделей: `windflow-v3`.** Обновлены три модели; четвёртая сохранена после сравнения. В API новые поля не требуются, метрики обновлены в прежнем endpoint. XGBoost обучен на RTX 4080, экспортированные деревья вычисляются через NumPy; при запуске приложения XGBoost и CUDA не нужны. README сейчас параллельно правится frontend-агентом; сведения о технологиях можно дополнить XGBoost CUDA (обучение) и NumPy (переносимый расчёт).

**Методика оценки v3:** настройки и веса смешивания подбирались на декабре внутри двух семейств экспериментов. Январь затем использован как проверочный период для принятия обновления: требовалось снижение MAE и RMSE. Поэтому январские результаты являются development-validation, а не независимым закрытым тестом. Это явно записано в `_meta` метрик и `models/optimization_report.json`; не заявлять обратное в интерфейсе или протоколе.

## Что уже работает

- FastAPI: синхронный прогноз, фоновые задания с polling, история, CSV, метрики.
- Реальные sklearn-модели и ансамбли для двух турбин и двух упреждений.
- Повторные запросы Open-Meteo с ограниченным backoff; проверка JSON, чисел и временной сетки; локальный кэш. Ошибка провайдера — HTTP 503, без выдуманной погоды.
- Семь настоящих этапов: `weather`, `validation`, `model_selection`, `features`, `forecast`, `quality`, `persist`.
- У каждого этапа: `status`, `started_at`, `finished_at`, `duration_ms`, `detail`, `metadata`. В weather metadata есть источник, число попыток и события retry/cache.
- SQLite сохраняет прогноз, provenance и журнал. Завершённые и неудачные фоновые задания доступны после перезапуска. Прерванные выключением процесса задания автоматически не возобновляются.
- Февраль: проверка полной сетки до расчёта, 28 выпусков, 672 часа на турбину. Повторный расчёт заменяет логический прогноз, не добавляет дубли. Неполный экспорт — HTTP 409.

Это детерминированная автономная оркестрация с правилами проверки, выбора модели и повторных запросов. LLM-вызовов и рассуждений языковой модели в pipeline нет; не представлять его как LLM-агента.

## API для интерфейса

Все существующие endpoint сохранены. Изменения полей добавочные.

```json
{
  "turbine_id": 1,
  "issue_date": "2026-01-29",
  "horizon_hours": 48,
  "data_mode": "offline"
}
```

`data_mode`: `auto` (сохранённый архив, затем сеть), `offline` (только архив), `live` (сеть).

| Действие | API |
|---|---|
| Готовность моделей | `GET /api/health` → `models_ready` |
| Запуск одного прогноза | `POST /api/jobs` с JSON выше → HTTP 202, `job_id` |
| Запуск февраля | `POST /api/jobs/february`; использовать `issue_date: "2026-01-31"`, `horizon_hours: 24`, `data_mode: "auto"` |
| Polling | `GET /api/jobs/{job_id}` каждые 500–1000 мс до `completed`/`failed` |
| История законченных заданий, включая ошибки | `GET /api/jobs?limit=20` |
| История сохранённых прогнозов | `GET /api/forecasts?limit=100` |
| Детали сохранённого прогноза | `GET /api/forecasts/{run_id}` |
| CSV прогноза | `GET /api/forecasts/{run_id}/export.csv` |
| CSV полного февраля | `GET /api/forecasts/february/export.csv?turbine_id=1` |
| Метрики | `GET /api/models/metrics` |
| Прогноз против факта | `GET /api/models/validation?turbine_id=1&lead_days=1` |

Задание возвращает `status`, `steps`, `progress`, `total`, `message`, `error`, `result`, `kind`, `request`, `created_at`.
При ошибке этап имеет `failed`, не начатые этапы остаются `pending`. Февраль выполняется по дням: этапы повторяются; общий прогресс отображать по `progress/total`, а не по количеству completed stages.

В `result` одного прогноза добавлены:

- `issue_at` — дата и время выпуска с `+05:00`, `created_at` — фактическое время расчёта.
- `data_source`: `open_meteo` = сеть, `cache` = локальный кэш, `bundled_archive` = сохранённая демо-выборка. `synthetic_test_fixture` встречается только в тестах.
- `model_version`, `model_artifacts[]`: версия, SHA-256 файла, `trained_through`, `available_from`, роль `validation`/`production`, упреждение.
- `weather_provenance`, `timing_note`, `quality_warnings`.
- `forecast[]`: мощность и границы диапазона в 0–1, ветер в м/с, температура °C. Для процентов мощности умножать на 100.
- `expected_normalized_energy` — нормированные турбино-часы, **не кВт·ч**: номинальная мощность не предоставлена.

Границы `confidence_low/high` сохранены для совместимости. Подпись в UI: **«Эмпирический диапазон ошибки»**. Не называть гарантированным 90% доверительным интервалом.

## Реальные метрики

Источник значений — `backend/models/metrics.json`. Не хардкодить таблицу в UI.

| Турбина | Часть прогноза | Часов оценки | MAE | RMSE | R² | Снижение MAE относительно wind_curve |
|---|---|---:|---:|---:|---:|---:|
| 1 | 1–24 ч | 744 | 0.145581 | 0.200797 | 0.645613 | 18.16% |
| 1 | 25–48 ч | 720 | 0.188971 | 0.241492 | 0.483670 | 6.18% |
| 2 | 1–24 ч | 744 | 0.151199 | 0.204320 | 0.633742 | 15.73% |
| 2 | 25–48 ч | 720 | 0.188395 | 0.243087 | 0.478161 | 6.62% |

- Ключи `turbine_1.day_1`, `turbine_1.day_2`, аналогично turbine_2. **day_2 — отдельно часы 25–48, не средняя метрика всего 48-часового прогноза.**
- `baselines.mean` и `baselines.wind_curve` оценены на тех же строках, что ML.
- `improvement_vs_baseline.wind_curve`: `mae_reduction`, `mae_reduction_percent`, `rmse_reduction_percent`, `r2_delta`. Положительное снижение — улучшение, отрицательное — ухудшение. Все четыре модели v3 превосходят wind_curve по MAE и RMSE на соответствующих строках январской проверки.
- `interval.coverage` — фактическое покрытие январских значений декабрьским диапазоном: примерно 96.10%, 94.58%, 97.31%, 92.92% соответственно. Это покрытие широкого диапазона, **не точность прогноза**.
- `interval.mean_width`, `validation_radius`, `production_radius`, `production_coverage: null` доступны из API.
- Цель R² ≥ 0.80 **не достигнута**.
- У обновлённых моделей `previous_version` содержит результаты v2 на тех же строках. Проверять `same_evaluation_rows` перед сравнением: у неизменённой модели turbine_2/day_2 остаётся более старая несопоставимая версия в этом поле.

## Как объяснять отсутствие утечки и ограничения

1. Признаки содержат только архивные прогнозы погоды и календарь. Будущий фактический ветер и мощность в признаки не входят.
2. Настройки выбираются по декабрю 2025. Валидационные модели не обучаются на январских целях. Production-модели переобучены по 31 января и применяются для февральских выпусков.
3. Выбор настроек и калибровка завершаются 31 декабря. Поэтому оценка day_1 — 1–31 января, day_2 — **2–31 января**: выпуск day_2 на 1 января был бы 30 декабря. Слишком ранний запуск отклоняется.
4. Январь уже просматривался в предыдущих экспериментах разработки и используется для принятия обновлений v3. Это хронологическая проверка при разработке, а не независимый закрытый тест. Указанные даты выбора настроек и обучения не означают, что финальная версия была исторически зафиксирована до января.
5. По [документации Open-Meteo](https://open-meteo.com/en/docs/previous-runs-api), `previous_day1/day2` — фиксированные упреждения 24/48 часов относительно каждого целевого часа. Это **не единый выпуск** метеомодели. При issue time 23:59:59 UTC+5 все номинальные origin times не позже выпуска; это проверяет код.
6. Архив не возвращает точное время публикации каждого исходного выпуска. Поэтому `publication_time_verified=false`, `weather_run=null`. Нельзя обещать доказанную минутную доступность всех исходных данных на исторический issue time. Для такой гарантии нужен архив с идентификаторами выпусков и временем доступности, отдельная интеграция и повторная оценка модели.
7. Диапазон — квантиль абсолютных ошибок. Декабрь также использован для выбора настроек, поэтому это не строго независимая conformal calibration. Покрытие проверяется на январе; для февраля пока неизвестно.

**Февральская погода пока не загружена в этой среде:** сетевой запрос блокируется. Полнота 672 часа и идемпотентность проверены автоматическими тестами на явно обозначенной синтетической погоде с настоящими моделями. Это не заменяет реальную февральскую демонстрацию.

Для завершения реального февральского прогона на машине с доступом к Open-Meteo:

В `backend/demo` уже есть небольшая январская выборка настоящей погоды для воспроизводимого демо; не путать её с исходными SCADA-данными.

## GPU и воспроизводимость

На RTX 4080 Laptop реально выполнены 112 конфигураций XGBoost 3.2.0/CUDA, суммарное время fitting около 53 секунд. Дополнительно проверены 80 CPU-конфигураций SVR и HistGradientBoosting. Результаты трёх моделей улучшены; turbine_2/day_2 оставлена прежней. Для двух экспортированных GPU-моделей предсказания NumPy и XGBoost совпали на всём январе (максимальная разница 0.0). Во время работы API видеокарта и пакет XGBoost не используются.

`scripts/train_models.py` воспроизводит выбор, оценку и production refit из исходных CSV и погодного архива. `scripts/refresh_metrics.py` проверяет метрики по сохранённым прогнозам и обновляет отчёт без переобучения; сохранены baseline_mean и baseline wind_curve.

Для воспроизведения оптимизации v3: сначала базовые модели, затем `scripts.experiment_xgboost`, `scripts.experiment_smooth`, `scripts.promote_optimized_models`. Для GPU-обучения нужен XGBoost 3.2.0; скрипты принимают `--extra-site-packages`, если библиотека уже установлена в отдельном локальном Python. Рабочая среда приложения не менялась. Исходные модели сохранены локально в игнорируемом `data_cache/pre_v3_models`; сводка их метрик включена в `models/metrics_before_v3.json`, протокол обновления — `models/optimization_report.json`.
