# Протокол прогноза и проверки

## Что именно прогнозируется

Почасовая средняя нормализованная активная мощность каждой турбины в шкале 0–1.
Сумма почасовых значений — эквивалент часов работы на номинальной мощности.
Для перевода в МВт и МВт·ч нужен номинал турбины, которого нет в исходных CSV.
Все часы интерфейса и экспорта относятся к UTC+5.

Выпуск датирован концом выбранного дня, 23:59:59 UTC+5. Например, выпуск 31 января
на 48 часов содержит 1 февраля 00:00 — 2 февраля 23:00. Это два следующих
календарных дня. Февральский пакет состоит из 28 выпусков на первые сутки,
с датами выпуска 31 января — 27 февраля: ровно 672 уникальных часа на турбину.

## Погодные данные и ограничение реконструкции

Используются архивные **прогнозы**, не фактическая будущая погода.
Open-Meteo Previous Runs возвращает значения с фиксированным упреждением:
`previous_day1` — 24 часа, `previous_day2` — 48 часов до прогнозируемого часа.
Для первого прогнозного дня используются первые поля, для второго — вторые.
Для первого дня допустимы также более старые прогнозы `previous_day2`.
Контекстные признаки вычисляются только внутри одного прогнозируемого дня.

Это реконструкция по фиксированному упреждению, **не единый метеорологический
выпуск с зафиксированным временем инициализации**. API не возвращает момент
публикации каждого значения. Поэтому утверждение о строгой доступности каждого
значения к определённой минуте выпуска в этой версии не доказано. Для такого
требования нужен переход на Single Runs API с фиксированным `run`, учётом задержки
публикации и повторной оценкой модели на том же источнике.

Источники: [Previous Runs](https://open-meteo.com/en/docs/previous-runs-api),
[Single Runs и задержка публикации](https://open-meteo.com/en/docs/single-runs-api).

## Разделение данных

1. Подбор параметров: обучение на истории до 1 декабря 2025, сравнение на декабре.
   Сравниваются признаки, окна истории, HistGradientBoosting, ExtraTrees,
   XGBoost и смеси моделей. Конфигурации и веса внутри каждого семейства
   выбираются по декабрю. Выбор сохранён в `model_selection.json` и
   `optimization_report.json`.
2. Проверочная модель: выбранная конфигурация обучается на истории до 1 января 2026.
   Отчёт считается отдельно для каждой турбины и дня горизонта: 744 часа для
   day 1 и 720 часов со 2 января для day 2, чтобы его выпуск находился после
   границы обучения.
   Для второго дня обучение заканчивается 30 декабря: прогноз на 1 января
   с упреждением два дня выпускается именно 30 декабря. Аналогичный зазор
   применяется к декабрьскому подбору. Это исключает обучение на данных,
   появившихся после самого раннего выпуска в проверочном месяце.
3. Январь используется как development-validation для проверки обновления:
   новая версия принимается только при согласованном улучшении MAE и RMSE.
   Поэтому январь не является скрытым независимым тестом.
4. Рабочая модель переобучается с добавлением января для февральских прогнозов.
   При январской проверке используются отдельные validation-модели.

Итоговая независимая оценка обобщения выполняется после получения фактических
значений мощности февраля. Все публикуемые январские метрики помечены как
development-validation и воспроизводятся из сохранённых почасовых прогнозов.

Будущие измерения ветра, температуры и мощности не входят в признаки.
Пропуски обучающей истории не заполняются будущими значениями. Для инференса
неполная временная сетка или нечисловая погода отклоняется с объяснением.
История производства начинается в 2023 году, но доступный сохранённый архив
прогнозов и выбранные окна ограничивают фактически используемые обучающие строки.

## Что проверяется в метриках

- MAE и RMSE относятся к шкале мощности 0–1, меньше — лучше.
- R² не означает долю точных прогнозов и не является «процентом точности».
- Сравнения: предыдущая версия, постоянное среднее обучения, простая монотонная
  зависимость мощности от прогнозируемого ветра.
- `validation_predictions.csv` содержит все факты, предсказания и простой прогноз
  для независимого пересчёта MAE/R².
- Оценочный диапазон — 90-й процентиль прошлых абсолютных ошибок. Для январской
  модели используются ошибки декабря, для февральской — ошибки января.
  Покрытие будущего прогноза не гарантируется; это не формальный доверительный интервал.

## Агент и воспроизводимость

Агент — детерминированный оркестратор с состояниями шагов, повторными запросами,
выбором сохранённого архива, проверкой полноты и сохранением результата. LLM не
используется. Журнал фиксирует действительное начало, завершение, длительность
и причину ошибки. Успешные журналы сохраняются в SQLite; текущие задания и ошибки
фоновых заданий сохраняются в SQLite и доступны в истории после перезапуска.

Часть моделей v3 обучена XGBoost с CUDA. Деревья экспортированы в переносимый
формат и выполняются через NumPy, поэтому для запуска API не требуются XGBoost,
CUDA или видеокарта. Равенство переносимого и исходного inference проверено
автоматическими тестами.

Сохранённая погода имеет описание происхождения и SHA-256 в `demo/manifest.json`.
Февральская модель и январская проверочная модель поставляются отдельно.
Офлайн-демо вычисляет прогноз заново из погоды и модели, не подставляет готовый ответ.
